Integrazione ERP e MES

Come un gestionale (ERP), un sistema di produzione (MES) o un PLC di linea crea, modifica, avvia ed elimina i work order di una postazione RTIndustry 2.0 e ne legge l'avanzamento.

Tutti i canali applicano le stesse regole: validazione dei dati, coda massima di 15 work order da fare, un solo work order in lavorazione, stato della licenza. Ogni operazione, anche rifiutata, è registrata sulla postazione con il canale di provenienza, utile per il supporto.

Attivazione

I canali si attivano in Impostazioni › Integrazione work order, riservata all'amministratore. La chiave per REST e MQTT si genera nella stessa sezione.

API REST: autenticazione

  • URL di base: http://<pc-macchina>:1880/api/erp (oppure https:// se sul PC è installato un certificato).
  • Formato: JSON UTF-8 in ingresso e in uscita.
  • Date: AAAA-MM-GG per la consegna; date e ore restituite come AAAA-MM-GG HH:mm:ss nel fuso orario della macchina.

Ogni richiesta deve avere l'header:

X-Api-Key: rti_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

La chiave è mostrata una sola volta: RTIndustry ne conserva solo l'impronta, quindi una chiave persa non si recupera ma si rigenera. Rigenerarla o revocarla la invalida subito.

SituazioneRisposta
Nessuna chiave generata503 API non attiva
Header assente o chiave errata401
Configurazione iniziale non completata409
Licenza in sola lettura o bloccata403 sulle scritture (le letture funzionano)

Leggere l'avanzamento — GET /workorders

ParametroEsempioSignificato
statusRUNNINGStato del work order
columnin_progressrequested, in_progress, done
sourceerperp, manual (dal Kanban), machine (creati dalla macchina)
updatedSince2026-09-27 08:00:00Solo work order aggiornati da questo momento (ora locale della macchina)

Risposta: { "workorders": [ ... ], "total": 42, "limit": 100, "offset": 0 }. Per un aggiornamento incrementale conviene interrogare ogni 1–5 minuti con updatedSince uguale al last_update più recente ricevuto.

Dettaglio: GET /workorders/{erp_id}, con l'erp_id codificato nell'URL (per esempio ODP-2026%2F0001). 404 se non esiste.

Modificare — PUT /workorders/{erp_id}

Stessi campi della creazione, tutti facoltativi (erp_id non è modificabile). I campi extra si fondono con quelli esistenti. Si può modificare anche un work order in lavorazione, per esempio per aumentare la quantità: lo stato non cambia.

Cambiare stato — POST /workorders/{erp_id}/status

{ "status": "RUNNING" }
  • status: RUNNING, PAUSED, STOPPED, COMPLETED, SET-UP, REWORK, MAINTENANCE, CLEANING, FAULT, oppure REQUESTED (torna in «Da fare»);
  • in alternativa column: requested, in_progress (= RUNNING), done (= COMPLETED).

RUNNING mette in pausa l'eventuale altro work order in lavorazione (uno solo alla volta); COMPLETED imposta la data di fine. Risposta: il work order aggiornato.

Eliminare — DELETE /workorders/{erp_id}

Eliminazione logica: il work order resta nello storico interno. 400 se è in lavorazione.

Tabella di scambio su database

Stesso contratto della versione 1: il sistema esterno scrive in writewo, RTIndustry elabora le righe e aggiorna readed; l'avanzamento si legge da readwo. Le tabelle possono stare:

  • nel database di RTIndustry, per software installati sullo stesso PC (readwo è una vista sempre aggiornata);
  • in un MySQL aziendale: RTIndustry si collega al database indicato, legge writewo e riscrive l'avanzamento in readwo. Il pulsante «Crea tabelle mancanti» crea le due tabelle con lo schema della versione 1. La password è conservata cifrata sulla postazione.

Il controllo avviene ogni 10 secondi (configurabile).

Ciclo di una riga

readed scritto dall'ERPSignificatoEsito scritto da RTIndustry
0Nuovo work order1 e kanbanwoid = id del work order in RTIndustry
2Work order modificato (anche se in lavorazione)1
5 (nuovo nella 2.0)Eliminare il work order1
  • 3 + rejectedreason: rifiuto della postazione (coda piena, work order in lavorazione non eliminabile, licenza in sola lettura). RTIndustry ritenta da sé ogni minuto.
  • 4 + rejectedreason: dati non validi (per esempio description mancante). L'ERP corregge la riga e rimette readed = 2.

L'identificativo del work order (erp_id) è l'id della riga di writewo. Le righe con serial o workstation valorizzati vengono elaborate solo dalla postazione corrispondente (tabella condivisa tra più macchine); se vuoti, le elabora qualsiasi postazione.

Cambiare stato

  • colonna status (nuova nella 2.0, facoltativa): RUNNING, PAUSED, COMPLETED, REQUESTED… con readed = 2. È un comando: dopo l'esecuzione RTIndustry la riporta a NULL, così una modifica successiva (per esempio della quantità) non annulla una pausa decisa dall'operatore;
  • colonna column della versione 1: in_progress o done. Per riportare in «Da fare» un work order già avviato usare status = 'REQUESTED'.
-- Nuovo work order
INSERT INTO writewo (readed, description, itemcode, quantity, duedate)
VALUES (0, 'Albero motore', 'AX-12', 200, '2026-10-15');

-- Avviarlo
UPDATE writewo SET status = 'RUNNING', readed = 2 WHERE id = 42;

-- Avanzamento
SELECT id, status, qty_done, qty_scrap, mwt_running FROM readwo WHERE id = 'ERP-42';

MQTT

Broker integrato sulla porta 1883 della postazione.

TopicDirezioneContenuto
{deviceSN}/readuscitaTelemetria (leggibile senza credenziali)
{deviceSN}/writeingressoComandi sui work order (solo client autenticati)
{deviceSN}/write/resultuscitaEsito di ogni comando
{deviceSN}/wouscitaEvento a ogni variazione di un work order esterno (anche dall'operatore o dalla produzione)

Autenticazione: nome utente libero (per esempio erp), password = chiave API (la stessa della REST). Credenziali errate: connessione rifiutata. Un client senza credenziali può leggere la telemetria, ma i suoi comandi vengono scartati. Nessun client può pubblicare su /read, /write/result o /wo.

Comandi

{ "id": "c-1", "action": "create", "erp_id": "ODP-1", "data": { "description": "Albero", "qty_requested": 10 } }
{ "id": "c-2", "action": "update", "erp_id": "ODP-1", "data": { "qty_requested": 12 } }
{ "id": "c-3", "action": "status", "erp_id": "ODP-1", "status": "RUNNING" }
{ "id": "c-4", "action": "delete", "erp_id": "ODP-1" }
{ "id": "c-5", "action": "get",    "erp_id": "ODP-1" }
{ "id": "c-6", "action": "list",   "data": { "status": "RUNNING" } }

data ha gli stessi campi della REST; id è un identificativo a scelta del mittente, restituito nell'esito.

Esiti ed eventi

{ "id": "c-4", "action": "delete", "erp_id": "ODP-1", "ok": false, "status": 400, "error": "Work order in lavorazione: impossibile eliminarlo", "codice": "in_lavorazione" }

{ "evento": "status", "eliminato": false, "workorder": { "erp_id": "ODP-1", "status": "RUNNING", "qty_done": 3 } }
